CONFIRMED DEFECTS FOUND IN THE EARLIER PATCH

1. Stripe advisory-lock scope was stronger than the row model. The lock key included test/live environment, but the order row did not persist environment. A pending order could therefore be ambiguous across configuration changes. The new repair persists stripe_environment and rejects legacy pending Stripe rows whose environment is unknown.

2. The owner payout UI still forced expected_environment = sandbox and displayed “Send with PayPal sandbox.” That could conflict with backend live configuration and made the client an unsafe environment authority. The new repair removes the client-side environment override and label.

3. PayPal process-creator-payout and sync-creator-payout silently defaulted an absent environment to sandbox. The new repair fails closed unless PAYPAL_ENV or PAYPAL_ENVIRONMENT explicitly resolves to live or sandbox.

4. PayPal recharge used only PAYPAL_ENVIRONMENT while payout functions accepted PAYPAL_ENV first. The new repair aligns recharge with the same explicit environment precedence used by payout functions.

5. Existing tests checked source markers but did not assert the new Stripe environment-isolation invariant or strict PayPal process/sync gates. New contract tests were added for those exact policies.

PURCHASE REPAIR

Changed:
supabase/functions/stripe-checkout-session/index.ts
supabase/migrations/20261023210000_build46_stripe_checkout_lock.sql

The migration adds coin_recharge_orders.stripe_environment and an index for pending Stripe orders. The service-role-only create_stripe_recharge_order database function takes a user, pack, environment, amount, currency, and coin count. It serializes order creation with pg_advisory_xact_lock using user, pack, and environment. It reuses only a pending order with the same persisted environment and exact economic fields.

If a legacy pending Stripe row has a null environment, the function raises a reconciliation-required error. The Checkout edge function returns HTTP 409 with stripe-legacy-order-reconciliation-required instead of guessing. If a matching pending row already has a provider session ID, the function returns HTTP 409 with stripe-checkout-already-pending rather than opening another provider session.

The existing server-only fulfillment boundary remains unchanged: Checkout creation does not credit coins, the browser return page does not credit coins, and signed Stripe webhook fulfillment remains the crediting path.

PAYOUT REPAIR

Changed:
supabase/functions/process-creator-payout/index.ts
supabase/functions/sync-creator-payout/index.ts
native/flutter_v1/lib/features/profile/owner_control_center_build23.dart

Both PayPal provider functions now fail closed with paypal_environment_not_configured unless the configured value is exactly live or sandbox. The owner UI no longer injects expected_environment: sandbox and no longer claims that every payout is a sandbox payout. The backend remains the only environment authority.

The existing payout reservation protections were reviewed and retained. begin_creator_payout_processing locks the payout row, permits only approved or explicitly recoverable unknown submissions, and moves the request to processing/SUBMITTING. PayPal requests use a deterministic payout ID as PayPal-Request-Id and sender_batch_id. Ambiguous network/provider outcomes stay processing and reserved. review_creator_payout rejects terminal failure without provider-confirmed failure and rejects paid unless PayPal SUCCESS is recorded. The ledger debit uses payout:<id> as a conflict-safe source key.
